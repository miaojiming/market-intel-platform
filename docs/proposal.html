1. 背景与目标

1.1 业务背景

面向支付行业中的收单业务和银行 IT 领域，构建一个市场智能情报与获客平台。核心目标是从公开信息源自动采集行业动态，利用 AI 生成结构化情报摘要，并识别潜在商业机会（如收单机构、银行的系统改造需求）。

1.2 核心目标

快速出产品

2 天内完成 MVP，聚焦必要功能，控制风险

验证 AI 工程化

用 AI Evals 框架验证 AI 系统质量可量化、可回归

聚焦收单

收单费率、系统招标、监管政策、核心系统替换

银行 IT

独立部署的收单系统、银行核心系统改造也是机会

1.3 商业逻辑

行业情报采集 → AI 摘要 + 重要性评级 → 高价值线索识别 → 客户画像 → 获客触达

重点关注信号：
  - 收单费率变动（竞争加剧信号）
  - 银行收单系统招标/改造（直接商机）
  - 核心系统替换（系统供应商机会）
  - 监管政策变化（合规需求）
  - 收单机构重大合约变更（供应商切换机会）

4.1 情报采集（intelligence.py）

数据源

来源类型地址
FinextraRSShttps://www.finextra.com/rss/headlines.aspx
The PaypersHTMLhttps://thepaypers.com/news

采集流程

1. 从 RSS 源解析 feed（feedparser）
2. 从 HTML 列表页提取文章链接（BeautifulSoup）
3. 按 cutoff_time 过滤（只保留最近 N 小时）
4. MD5 去重
5. 抓取文章全文（httpx + BeautifulSoup）
6. 返回结构化数据：
   {
     "id": "a1b2c3d4",
     "title": "Fiserv cuts acquiring rates...",
     "link": "https://www.finextra.com/...",   ← 真实文章 URL
     "source_name": "Finextra",
     "published": "2026-08-30T10:00:00",
     "summary_rss": "原文摘要...",
     "content": "全文内容..."
   }

4.2 LLM 封装（llm.py）

核心特性

  • OpenRouter API：支持多模型切换（GLM-5.3-Flash、Qwen-2.5-7B 等）
  • 重试机制：最多 4 次重试，指数退避（3s → 6s → 9s → 12s）
  • JSON 提取：多策略提取（直接 parse → 正则提取 → 文本搜索）
  • 字段归一化：兼容中英文字段名（"摘要" → "summary_zh"、"关键词" → "tags"）
  • SSL 兼容：使用 requests 替代 httpx，解决 macOS LibreSSL 问题

关键代码

4.3 摘要 Prompt（summarize.txt）

你是一名支付行业的收单与银行 IT 情报分析师。

要求：
1. 中文摘要，80字以内，严格基于原文
2. 2-4 个关键词标签（收单、银行IT、核心系统、费率...）
3. 重要性 1-5 分（5分=费率变动/招标/系统替换）
4. 标注信息来源名称和原始链接
5. 直接输出 JSON，不输出推理过程

输出格式：
{
  "summary_zh": "中文摘要",
  "tags": ["收单", "费率"],
  "importance": 5,
  "source_name": "Finextra",
  "source_url": "https://..."
}

5. AI 工程化实践 — AI Evals

核心理念：AI 系统的质量必须可量化、可回归、可门禁。不能靠"感觉"判断 AI 输出好坏，需要建立自动化评测体系。

5.1 什么是 AI Evals

AI Evals 是借鉴软件工程中测试驱动开发的理念，对 AI 系统的输出进行自动化质量评估。核心组成：

  • 评测集（Goldens）：人工标注的输入 + 预期输出
  • 评测指标（Metrics）：多维度打分（格式合规、真实性、综合质量）
  • 门禁阈值（Thresholds）：低于阈值即不通过，退出码非零
  • 基线对比（Baseline）：保存历史成绩，检测回归

5.2 评测框架设计（Harness 风格）

配置文件（intelligence.eval.yaml）

eval_name: intelligence_summary
description: 收单与银行IT情报摘要质量评测

metrics:
  - name: schema_validation
    threshold: 1.0
    weight: 0.2
    description: 输出格式是否合规（必填字段齐全 + 类型正确）

  - name: faithfulness
    threshold: 0.85
    weight: 0.4
    description: 摘要是否真实反映原文（不编造信息）

  - name: geval
    threshold: 0.7
    weight: 0.4
    description: 综合质量（LLM-as-judge，多维度评分）

target:
  model: z-ai/glm-5.3-flash
  temperature: 0.3

dataset: eval/goldens.jsonl

三个评测指标

格式合规（Schema Validation）

权重 20% | 阈值 1.0

检查输出是否包含所有必填字段（summary_zh, tags, importance, source_name, source_url），类型正确（tags 是数组，importance 是数字）

真实性（Faithfulness）

权重 40% | 阈值 0.85

LLM-as-judge 评估摘要中的每个声明是否能在原文中找到依据，防止 AI 编造信息

综合质量（GEval）

权重 40% | 阈值 0.7

LLM-as-judge 多维度评分：摘要准确性、标签相关性、重要性判断合理性（0-1 分）

门禁机制

# run_eval.py 退出逻辑
if all([
    avg_schema >= THRESHOLDS['schema_validation'],
    avg_faith >= THRESHOLDS['faithfulness'],
    avg_ge >= THRESHOLDS['geval'],
]):
    print("✅ 门禁通过")
    sys.exit(0)   # CI/CD 可继续
else:
    print("❌ 门禁未通过")
    sys.exit(1)   # CI/CD 阻断部署

6.2 v2 改进说明

  • Prompt v2 新增："严格基于原文，不得添加原文中没有的数字、日期、金额"
  • 来源字段：新增 source_name + source_url，每条摘要可追溯
  • 真实性提升：0.73 → 0.81（case-003 汇丰、case-006 工行从 0 分升到 1.0）
  • 格式略降：1.0 → 0.92（case-013 JSON 提取失败，reasoning 模型 token 截断）

6.3 真实性问题分析

GLM-5.3-Flash 的"推理补全"问题

模型倾向于基于常识推理"补全"原文中未明确的具体数字（合同金额、预算、TPS、完成时间）。v2 Prompt 加入"严格基于原文"约束后有所改善，但仍有 2-3 条用例存在此问题。

6.4 评测结论

AI Evals 工程化实践验证成功 ✅

1. 评测框架稳定，13 条用例全部跑通

2. 能准确区分不同模型的质量差异（Qwen 0.37 vs GLM 0.86）

3. 粒度细，能定位到具体哪条用例、哪个指标有问题

4. 门禁机制有效，低于阈值即阻断

5. 基线对比功能就绪，支持"改 Prompt → 跑评测 → 对比基线"的迭代闭环

7. 遇到的问题与解决方案

问题原因解决方案
OpenRouter 403 Forbidden 缺少 HTTP-Referer 和 X-Title 请求头 添加 OpenRouter 要求的 Headers
SSL EOF 错误（httpx） macOS Python 3.8 使用 LibreSSL，与 OpenRouter TLS 不兼容 从 httpx 切换到 requests 库
LLM 输出 JSON 解析失败 Qwen 模型输出包含 markdown 代码块、多余文本 多策略 JSON 提取（直接 parse → 正则 → 文本搜索）
中文字段名不匹配 LLM 输出 "摘要" 而非 "summary_zh" 字段归一化映射（FIELD_MAP 支持中英文别名）
GLM reasoning 模型输出截断 推理过程占用 token，最终 JSON 未输出 Prompt 加"直接输出 JSON，不输出推理" + 增大 max_tokens 到 2000
真实性低（编造数字） GLM 基于推理"补全"原文没有的具体信息 Prompt 加"严格基于原文，不得添加原文没有的数字"
评测集来源链接不可点击 测试数据是人工编写，URL 为占位符 实际系统从 RSS 抓取真实文章 URL（intelligence.py 的 link 字段）

8. 关键发现

8.1 模型选择至关重要

Qwen 2.5 7B 综合质量 0.42，GLM 5.3 Flash 达到 0.88——同一套 Prompt 和评测框架，模型差异带来 2 倍质量差距。AI Evals 能量化这种差异，为模型选择提供数据支撑。

8.2 Prompt 优化可量化

加入"严格基于原文"约束后，真实性从 0.73 提升到 0.81。每一次 Prompt 修改的效果都可以通过评测数据验证，而不是靠主观感受。

8.3 评测集设计需要覆盖边界

13 条用例包含 2 条噪音文章（健身房、Salesforce 财报），评测框架能正确识别它们并给出低分，说明 importance 评级逻辑有效。

8.4 "推理补全"是小模型的通病

GLM-5.3-Flash 的 reasoning 能力导致它倾向"补全"信息。这在使用更大模型（GPT-4o、Claude）时可能会更轻微，但任何 LLM 都需要真实性评测来兜底。

8.5 AI Evals 是 AI 工程化的基础设施

传统软件有单元测试，AI 系统需要 AI Evals。两者逻辑一致：

· 测试集 = 黄金标准用例

· 断言 = 评测指标 + 阈值

· CI 门禁 = 评测门禁（低于阈值阻断部署）

· 回归检测 = 基线对比（新版本不能低于历史最佳）

9. AI-DLC 工程化方法论

背景：AWS 开源了 AI-DLC（AI-Driven Development Life Cycle） 方法论，核心思想是将 AI 定位为开发流程的中央协作者——AI 创建计划、提出澄清问题、获得人类验证后才执行。我们将其三阶段自适应工作流融入本项目的工程化落地。

9.1 AI-DLC 三阶段模型

AI-DLC 将软件开发分为三个自适应阶段，每个阶段为下一个阶段提供更丰富的上下文 [$TRAE_REF](https://aws.amazon.com/blogs/devops/ai-driven-development-life-cycle/)：

阶段核心目标关键活动本项目映射
Inception 确定"做什么"和"为什么" 需求分析、用户故事、应用设计、工作单元拆分、风险评估 已完成：收单+银行IT 聚焦、MVP 范围、风险剔除（LinkedIn 反爬）
Construction 确定"怎么做" 组件设计、代码生成、构建配置、测试策略、质量验证 已完成：5 个模块开发、LLM 集成、AI Evals 框架、13 条评测用例
Operations 部署与监控 部署自动化、基础设施即代码、监控与可观测性、生产就绪验证 待落地：CI/CD 评测门禁、定时任务部署、监控告警

9.2 AI-DLC 五大原则与本项目对齐

原则AI-DLC 定义本项目落地状态差距与改进
自适应智能 只执行对特定请求有价值的阶段 部分实现：评测框架按场景跳过不适用指标 增加条件化评测（噪音文章跳过真实性评估）
上下文感知 分析现有代码库和复杂度要求 LLM 接收完整文章+来源信息作为上下文 增加历史情报上下文传递（多轮记忆）
基于风险 复杂变更全面处理，简单变更保持高效 AI Evals 门禁阈值按指标分级（格式 1.0 > 真实 0.85 > 综合 0.7） 增加动态阈值（噪音文章降低质量要求）
问题驱动 通过结构化文件提问，而非聊天 Prompt 模板以 JSON 结构化输出要求 增加多轮澄清机制（低置信度时追问）
始终可控 审查执行计划并批准每个阶段 评测门禁人工审批、评测结果可视化报告 增加 CI/CD 门禁 + 人工审核流程

9.3 落地行动：将 AI-DLC 融入工程流程

Construction 阶段补强

上下文持久化

AI-DLC 强调跨会话上下文持久化。当前评测结果和 Prompt 版本已存为 JSON/文件。下一步：将情报摘要存入数据库，支持历史检索和趋势分析。

问题驱动澄清

当 LLM 置信度低（重要性=3 且真实性<0.5）时，自动追加澄清问题："这是否涉及收单系统改造？请明确商机类型"。

Operations 阶段建设（重点）

CI/CD 评测门禁

每次 Prompt 或模型变更时，CI 自动运行 python eval/run_eval.py，门禁通过（exit 0）才允许合并。低于基线时发出回归告警。

定时情报采集部署

APScheduler 定时任务部署到 Linux 服务器（解决 SSL 问题），每日 8:00 自动采集 + 摘要 + 推送飞书。

监控与可观测性

记录每次 LLM 调用的耗时、Token 消耗、成功率。监控指标：情报采集成功率、摘要质量评分趋势、API 错误率。

生产就绪验证

上线前 Checklist：SSL 兼容性、API Key 有效性、飞书 Webhook 连通性、评测门禁通过、基线保存完毕。

9.4 AI-DLC 与 AI Evals 的关系

AI-DLC 是方法论框架，AI Evals 是质量保障工具

AI-DLC 的 Construction 阶段要求"质量保证和验证"——这正好对应我们的 AI Evals 评测框架。

AI-DLC 的 Operations 阶段要求"生产就绪验证"——这对应 AI Evals 的 CI/CD 门禁机制。

本项目已走通了 AI-DLC 的前两个阶段（Inception + Construction），下一步重点建设 Operations 阶段。
